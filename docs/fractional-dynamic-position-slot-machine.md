Fractional Dynamic Position Slot Machine Specification

1. Architectural Design and State Entities

The Fractional Dynamic Position Slot Machine is a deterministic execution engine
designed to manage leveraged derivative positions on a portion-by-portion basis.
This system decomposes a standard unified position into a multi-part lifecycle
managed across four discrete, state-tracked execution units. By separating the
consolidated position from its constituent entries, the system achieves precise
risk scaling and granular execution tracking.

The state of any open position is split across three synchronized database
tables in your SQLite schema to enforce strict referential integrity and
transaction safety:

1.  active_positions (The Master Record): This table maintains the high-level
    state of the active trade cycle. It persists the baseline metrics of the
    trade, including initial_allocated_margin (the total capital committed at
    cycle inception) and realized_pnl_accumulator (the cumulative realized
    profits or losses generated by portions scaled out during the active cycle).
    It also exposes the dynamic aggregates—such as total size, total allocated
    margin, and weighted average entry price—which are recalculated upon any
    state change.
2.  position_slots (The Portion Records): This table manages the individual
    portions. To prevent memory fragmentation and enforce strict scaling
    boundaries, exactly four slots are available per symbol, mapped to database
    slot indices 0, 1, 2, and 3. Each row maintains its own private execution
    metadata, including entry_price, size (units), allocated_usd (margin),
    realized_pnl, and timestamp (the exact millisecond of execution used to
    order the FIFO queue).
3.  trade_telemetry_history (The Audit Record): This table holds immutable
    historical records of completed trade executions. To ensure that
    paper-traded slots can be audited by the asynchronous AI journaling agent
    without violating database referential integrity, every closed slot is
    mirrored here as a completed trade under the exchange label 'PAPER' prior to
    committing the slot deallocation transaction.

2. Mathematical Modeling & Capital Allocation

The core of this position state machine is the dynamic calculation of margin and
size for each portion. Rather than allocating fixed, rigid nominal amounts, the
engine calculates the capital allocated to each newly opened slot based on the
remaining unallocated capital in the active trade cycle.

2.1 Cycle Capital (C_{\text{cycle}})

At the start of a fresh trade cycle (when no position exists), C_{\text{cycle}}
is initialized to the base margin allocation specified by the risk profile or
the account configuration: C_{\text{cycle}} = I_{\text{margin}} Where
I_{\text{margin}} is the initial allocated margin at cycle inception (e.g.,
\$10,000).

If a position is already active, the total capital pool for the cycle is the sum
of the initial margin and any realized gains or losses accumulated from closed
portions during the current active cycle:
C_{\text{cycle}} = I_{\text{margin}} + R_{\text{accum}} Where R_{\text{accum}}
is the realized_pnl_accumulator from the active_positions table.

2.2 Unallocated Capital (U_{\text{cycle}})

The unallocated capital represents the remaining funds in the cycle that have
not yet been committed to active slots:
U_{\text{cycle}} = C_{\text{cycle}} - \sum_{i \in \text{Active}} K_i Where K_i
is the margin locked in active slot i.

2.3 Weighted Slot Margin (K_{\text{new}})

When opening a new portion slot, the engine calculates the margin allocation
(K_{\text{new}}) for the next vacant slot. This calculation incorporates a
weighting coefficient (W), representing the dynamic slot scaling parameter
(which is currently defined as a configurable variable set to a default value of
1.0):
K_{\text{new}} = \left( \frac{U_{\text{cycle}}}{N_{\text{vacant}}} \right) \times W
Where N_{\text{vacant}} is the number of remaining inactive slots (ranging
from 1 to 4).

2.4 Slot Unit Size (S_i)

The actual trade size in base cryptocurrency units (S_i) for a newly opened slot
i is calculated from the computed margin allocation (K_{\text{new}}), the
asset's entry price (P_{\text{entry}, i}), and the leverage factor (L):
S_i = \frac{K_{\text{new}} \times L}{P_{\text{entry}, i}}

2.5 Portions Inequality and Equalization Mechanics

Because individual slots can be opened and closed at different prices, the
nominal sizes and margins of active slots will not be equal during a
scale-in/scale-out sequence. If a portion is closed in profit, C_{\text{cycle}}
expands, which means that any subsequent re-entry will be calculated with a
larger portion size.

This inequality is an intentional feature of the compounding model. The portions
do not equalize during an active trade cycle. They are equalized (reset to a
clean, equal slate) only when the entire position is fully closed. When the
active slot count reaches zero, the trade cycle is terminated,
realized_pnl_accumulator resets to 0.0, and the next trade cycle starts fresh
with all 4 starting slots equal (each at C_{\text{cycle}} / 4).

3. Portfolio Valuation and Real-Time State Fluctuation

To maintain strict data integrity, the system draws a sharp distinction between
nominal database states and real-time valuation parameters.

3.1 Constant Nominal Parameters

Once a slot is successfully opened and its transaction is committed to the
database, its allocated margin (K_i) and its unit size (S_i) are permanently
locked in the position_slots table. These values represent the historical cost
basis of the portion and are never modified during price fluctuations.

3.2 Real-Time Valuation Fluctuation

The current market valuation of the active slots fluctuates continuously with
incoming price ticks. The unrealized P&L (U_i) of each active slot is calculated
dynamically on-demand:
\text{Long Slot: } U_i = (P_{\text{current}} - P_{\text{entry}, i}) \times S_i
\text{Short Slot: } S_i \text{ is Short} \implies U_i = (P_{\text{entry}, i} - P_{\text{current}}) \times S_i
Where P_{\text{current}} is the latest mark price from the WebSocket feed.

The total real-time value (V_{\text{cycle}}) of the active position cycle is the
sum of the nominal margins of all active slots and their collective unrealized
P&L:
V_{\text{cycle}} = \sum_{i \in \text{Active}} K_i + \sum_{i \in \text{Active}} U_i

The consolidated unrealized ROI % is calculated relative to the total margin
currently committed:
\text{Unrealized ROI \%} = \left( \frac{\sum_{i \in \text{Active}} U_i}{\sum_{i \in \text{Active}} K_i} \right) \times 100

4. Portion Synchronization, Recalculation, and Transaction Boundaries

Whenever a new portion is opened or closed, the master active_positions record
must be recalculated to maintain a synchronized representation of the
consolidated position.

To prevent rounding errors and float drift, the master metrics are not modified
incrementally. Instead, they are completely recalculated from scratch using the
active rows in position_slots.

4.1 Consolidated Metrics

The re-aggregation calculations are executed within a unified database
transaction:

1.  Total Consolidated Size (S_{\text{total}}):
    S_{\text{total}} = \sum_{i \in \text{Active}} S_i
2.  Total Consolidated Margin (K_{\text{total}}):
    K_{\text{total}} = \sum_{i \in \text{Active}} K_i
3.  Weighted Average Entry Price (P_{\text{avg}}):
    P_{\text{avg}} = \frac{\sum_{i \in \text{Active}} (P_{\text{entry}, i} \times S_i)}{S_{\text{total}}}

The master row in active_positions is updated with these synchronized values,
and current_portions is set to match the active row count in position_slots.

4.2 Transactional Boundaries

All slot modifications use database transaction pipelines in
crates/engine/src/paper_trading.rs to ensure atomicity. If any step fails (such
as updating the balance, inserting a slot, or recalculating aggregates), the
entire transaction rolls back, preserving the previous state.

SQLite Write-Ahead Logging (WAL) mode is enabled to allow concurrent read
queries to complete without being blocked by active write transactions.

5. FIFO Scale-Out, P&L Realization, and Exit Sequences

The protocol strictly enforces First-In, First-Out (FIFO) queue mechanics when
executing partial position closures. This ensures that the oldest committed
capital is deallocated first.

5.1 Step-by-Step FIFO Execution Lifecycle

1.  Oldest Portion Identification: The engine queries the database to select the
    active slot with the minimum timestamp:
    \text{Target Slot } j = \min_{i \in \text{Active}} (\text{timestamp}_i)
2.  P&L Realization: The P&L for slot j is calculated based on its specific
    entry price (P_{\text{entry}, j}) and size (S_j), independent of the master
    average entry price:
    \text{Long Position: } PnL_j = (P_{\text{exit}} - P_{\text{entry}, j}) \times S_j
    \text{Short Position: } PnL_j = (P_{\text{entry}, j} - P_{\text{exit}}) \times S_j
3.  Accumulator Update: The realized P&L is added to the running cycle
    accumulator in active_positions:
    R_{\text{accum}} \leftarrow R_{\text{accum}} + PnL_j
4.  Capital Refund Calculation: The original margin allocated to slot j (K_j)
    plus the realized PnL_j (net of transaction fees and funding interest) is
    calculated as the total refund amount:
    \text{Refund} = K_j + PnL_j - \text{Fees}_{\text{commission}} - \text{Fees}_{\text{funding}}
    This refund is added directly to the user's current cash balance in
    paper_balances.
5.  Slot Deallocation: The targeted slot record is marked as inactive (is_active
    = 0), and its realized P&L is persisted in position_slots.
6.  Referential Integrity Mirroring: To ensure the asynchronous AI trade auditor
    can process the closed portion without violating database constraints, a
    record is inserted into the trade_telemetry_history table within the same
    transaction. This record mirrors the slot's performance metrics and is
    assigned the exchange label 'PAPER'.
7.  Transaction Commit: The transaction commits, ensuring atomicity across the
    slot deallocation, cash refund, and telemetry mirror.
8.  Re-Aggregation: recalculate_position_aggregates is called to recalculate and
    update the master position's size, average entry price, and margin. If no
    active slots remain, the entire position structure and its associated
    resting bracket orders are cleared from the active tables.

6. RESTING ORDER & BRACKET CONSTRAINT SYSTEM

To prevent logical conflicts, double-fills, and orphaned order executions, the
engine strictly enforces a 1-to-1 resource mapping.

6.1 Entry Order Constraints

Pending limit or stop entry orders represent potential vacant slots. You cannot
place more entry orders than you have available capacity in the trade cycle:
\text{Pending Entry Orders Count} \le N_{\text{vacant}} If the cycle has 2
active slots (N_{\text{vacant}} = 2), the maximum number of resting entry orders
allowed on the book is 2. Any attempt to place a 3rd entry order is blocked by
the API handler.

6.2 Exit Bracket Constraints

Take-profit (TP) and stop-loss (SL) bracket orders must be executed as
reduce_only orders and must map directly to the unique ID of an active slot.
\text{Active TP Orders Count} \le \text{Active Slots Count}
\text{Active SL Orders Count} \le \text{Active Slots Count} For every active
slot, there can be at most one associated take-profit limit order and one
associated stop-loss stop order. This prevents "double-killing" or creating
orphaned positions.

6.3 The FIFO Bracket Cleanup Rule

When a slot is deallocated via a manual or automated exit, the engine must
immediately delete the oldest active take-profit order and stop-loss order
associated with that position ID. This prevents the execution of "orphaned"
bracket orders if the price reverses back through the historical exit levels.

7. AUTOMATED PROTECTION & INVALIDATION SAFEGUARDS

The state machine implements two automated risk-mitigation systems to protect
cycle capital.

7.1 Break-Even Trailing Mechanics

The break-even trailing logic (check_break_even_trail in
crates/engine/src/paper_trading.rs) is evaluated whenever the market price
touches an active limit take-profit order.

  - Trigger: When the first take-profit target (TP_1) is hit and filled, the
    engine deallocates the corresponding slot.
  - Execution: The engine immediately updates the final_invalidation_level of
    the master position to match the weighted average entry price
    (P_{\text{avg}}).
  - Result: The stop-loss for all remaining active slots is moved to the
    break-even price, guaranteeing that the remainder of the trade cycle cannot
    result in a net capital loss.

7.2 Decisive Close Invalidation Mechanics

The invalidation logic (check_decisive_close_invalidation in
crates/engine/src/automation.rs) protects the position against structural
breakdown on closed candles, filtering out intra-candle wicks.

  - Trigger: The engine evaluates the closing price of completed 1-minute
    candles against the final_invalidation_level.
  - Tolerance Buffer: To filter out noise, the close must break beyond the
    invalidation level by more than a 0.2% tolerance buffer:
    \text{Long Invalidation: } \text{Close} < \text{SL} \times 0.998
    \text{Short Invalidation: } \text{Close} > \text{SL} \times 1.002
  - Execution: If a candle closes beyond this boundary, a market order is
    immediately executed to liquidate all remaining active slots in the cycle.
    This prevents premature invalidations caused by brief, illiquid price spikes
    that immediately return inside the boundary.

8. OPERATIONAL FRICTION & FEE DECAY MODELING

To prevent cash calculation mismatch between paper trading and real-world
execution, the engine models trading friction.

8.1 Fee and Interest Deductions

Each slot execution incurs trading fees and funding costs that must be deducted
directly from the cycle capital to prevent margin calculation mismatch:

1.  Commission Fee Deduction:
    \text{Fees}_{\text{commission}} = S_i \times P_{\text{execution}} \times \text{Rate}_{\text{exchange}}
      - Maker Fee Rate: 0.02% (limit orders)
      - Taker Fee Rate: 0.06% (market / stop orders)
2.  Funding Fee Deduction (Holding Cost): For overnight holdings, interest is
    accrued every 8 hours and deducted from the slot's margin:
    \text{Fees}_{\text{funding}} = S_i \times P_{\text{mark}} \times \text{Funding Rate}_{\text{8h}}

These friction costs are deducted from the cash refunded to paper_balances and
are debited from R_{\text{accum}}, ensuring that C_{\text{cycle}} reflects your
actual net capital, protecting the system against cash leakage over thousands of
simulated trades.

9. LOGICAL & STRUCTURAL VERIFICATION

To prove that the Fractional Dynamic Position Slot Machine is free of logical
deadlocks, race conditions, or inconsistent states, we model the system states
using formal verification rules and logic checks.

9.1 Logical State Transition Verification

Let A represent the active slot count, N_v represent vacant slots, and Cash
represent the paper account balance:

  - Rule 1 (Inception): If A = 0 and N_v = 4, an Open Slot trigger is valid if
    and only if Cash \ge K_{\text{new}}, where
    K_{\text{new}} = C_{\text{cycle}} / 4. Upon success, Slot 0 is initialized
    with is_active = 1, Cash is debited by K_{\text{new}}, and the master
    position is created.
  - Rule 2 (Inception Rejection): If A = 0 and N_v = 4, an Open Slot trigger
    with Cash < K_{\text{new}} is rejected. The transaction rolls back, and no
    database changes are written.
  - Rule 3 (Scaling-In): If 1 \le A < 4, another Open Slot in the same direction
    is valid if Cash \ge K_{\text{new}}, where
    K_{\text{new}} = U_{\text{cycle}} / N_{\text{vacant}}. Upon success, the
    next vacant slot is initialized, Cash is debited by K_{\text{new}}, and
    master aggregates are updated.
  - Rule 4 (Hedging Rejection): If 1 \le A < 4, an Open Slot in the opposite
    direction is rejected. Dual-hedged states (simultaneous long and short slots
    on the same symbol) are strictly prohibited.
  - Rule 5 (FIFO Scale-Out): If 1 \le A \le 4, a Close Portion trigger
    identifies the slot j with the oldest timestamp. P&L is calculated, Cash is
    credited by K_j + PnL_j - \text{Fees}, R_{\text{accum}} is updated, and slot
    j is marked inactive. If the remaining slot count is greater than zero,
    master aggregates are updated.
  - Rule 6 (Cycle Termination): If A = 1 and a Close Portion trigger occurs, the
    final slot is closed. Upon deallocation, the master active_positions row,
    associated position_slots records, and resting open orders are deleted,
    resetting the cycle state to Flat.
  - Rule 7 (Ceiling Restriction): If A = 4 (N_v = 0), any incoming Open Slot
    trigger is rejected. The system is fully allocated.
  - Rule 8 (Hard Stop Liquidation): If price crosses the invalidation boundary
    on a completed 1-minute candle, a complete liquidation occurs. All active
    slots are market closed, resting orders are cancelled, and the cycle state
    is reset to Flat.

9.2 Order Book and Bracket Constraint Verification

Let A be the number of active slots, E be the number of pending entry orders, TP
be the number of active take-profit bracket orders, and SL be the number of
active stop-loss bracket orders:

  - Constraint 1 (Resting Entries): The condition E \le N_{\text{vacant}} must
    remain true at all times. Placing a new entry order is permitted if and only
    if E + 1 \le 4 - A. Any order exceeding this limit is rejected by the API
    handler, preventing over-allocation.
  - Constraint 2 (Active Brackets): The conditions TP \le A and SL \le A must
    remain true at all times. Adding a bracket order is permitted if and only if
    the count of active brackets of that type does not exceed the count of
    active slots.
  - Constraint 3 (Entry Execution): When a pending entry order is filled, E is
    decremented by 1, A is incremented by 1, and a new slot is opened. The
    engine automatically creates corresponding TP and SL brackets for the new
    slot, maintaining TP = A and SL = A.
  - Constraint 4 (FIFO Exit Cleanup): When an active slot is closed, A is
    decremented by 1. The engine automatically deletes the oldest active TP
    order and SL order from the database, maintaining the TP \le A and SL \le A
    constraints and preventing orphaned execution.
